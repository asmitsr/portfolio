# settle up a group in as few transfers as possible
def settle_up(balances):
    # balances: {member: net} — positive means "is owed money"
    owes = sorted((m for m in balances if balances[m] < 0),
                  key=lambda m: balances[m])
    owed = sorted((m for m in balances if balances[m] > 0),
                  key=lambda m: -balances[m])
    return match_transfers(owes, owed)  # e.g. B -> A 300, C -> A 300

01

Password Leak Checker

FeaturedWEB · LIVE

Checks whether a password or email has appeared in known data breaches, and rates password strength — the lookup never stores what you type.

✓ Privacy by design — nothing you type into this checker is ever stored.

PythonFlaskBreach APIs
Case study — problem, build & outcome
Problem
People reuse the same password everywhere and have no quick way to tell whether it has already leaked in a breach.
Built
A Flask backend that queries breach data through external APIs and rates password strength — nothing typed into the checker is ever stored.
Outcome
Live and public on Vercel — anyone can run a check right now from the Open Website button below.
Why this stack
Python + Flask — the job is one focused lookup: take a check, ask the breach data, send the answer back. A small Flask backend does exactly that, with nothing extra in the way.
Hard part
The checker asks for the most sensitive thing a person can type, so it had to be useful without keeping any of it. The fix is in the design, not in a setting: nothing typed into the checker is ever stored — the check runs, the answer comes back, and nothing is written down.
Trade-off
Storing nothing means there is no history to go back to — every check stands on its own. That is the deliberate price of the privacy design: privacy first, convenience second.

02

Expense Splitter

FeaturedWEB · LIVE

Splits group expenses fairly: create a group, add members and shared costs, and see exactly who owes whom — with 50 currencies to choose from, picked per group.

✓ Verified test — a 900 expense split three ways settles as exactly two transfers of 300.

PythonFlaskSQLiteChart.js
Case study — problem, build & outcome
Problem
Group trips and shared flats end in messy who-owes-whom maths that nobody wants to work out by hand.
Built
Flask + SQLite behind it: groups, members and shared expenses, a settle-up algorithm that minimises the number of transfers, and a currency picked per group at creation from 50 Asian currencies.
Outcome
Live on Vercel and verified end-to-end: a 900 expense split three ways settles as exactly two transfers of 300.
Why this stack
Python + Flask with SQLite — groups, members and expenses are structured records, and the balances are worked out on the server, so a lightweight database behind Flask covers the whole job.
Hard part
The settle-up algorithm: a group's balances can tangle into many possible payments, and the goal is to clear them all in as few transfers as possible. It sorts who owes against who is owed and matches them off until every balance reaches zero — the split.py snippet in the Skills section above shows the shape of it, and the verified test in the Outcome row above is it working.
Trade-off
Minimising transfers means the settlements don't mirror who originally spent what — someone may end up paying a person they never borrowed from directly. The choice was fewer, cleaner settlements over a payment trail that follows every single expense.

Asmit MCP Server

PYTHON · OPEN SOURCE

A public Python MCP server that gives AI tools a URL-checking tool — with SSRF protection built in, so a fetch can't be redirected onto an internal address.

✓ Version 0.1.0 — main branch CI green: 28 unit tests pass, ruff clean.

PythonMCPSSRF protection
Case study — problem, build & outcome
Problem
A tool that fetches URLs on request has to be careful about where those URLs actually lead — a link can redirect somewhere internal that was never meant to be reached.
Built
A public Python MCP server (version 0.1.0) that exposes a URL-checking tool, with SSRF protection built in: the IP is pinned and re-verified at every redirect step, so a fetch can't be steered to an internal address.
Outcome
Public on GitHub at version 0.1.0 — main branch CI green, with 28 unit tests passing and ruff clean.
Why this stack
Python — the server's job is small and focused: take a URL check, guard the fetch, report back. Python keeps that job direct, and the project is held to a checked standard — 28 unit tests and ruff, both green in CI on the main branch.
Hard part
SSRF protection that survives redirects: checking an address once is not enough, because a URL can redirect — and each redirect can point somewhere new. The IP is pinned and verified again at every redirect step, so the check holds all the way through the fetch, not just at the start.
Trade-off
Pinning and re-verifying the IP at every redirect step is stricter than a single check up front — the protection wins over the shortcut: safety on every hop, even when it means more checking per fetch.

HTMLCSSJavaScriptWeb Speech API
Case study — problem, build & outcome

Reading long text is hard for people with low vision or reading difficulties, and Bengali text-to-speech support is especially thin.
Built
A single 24 KB HTML file on the Web Speech API: read-aloud in Bengali (bn-BD) and English (en-US), word-by-word highlighting as it speaks, and speed, font-size and theme controls — all processing stays on the device.
